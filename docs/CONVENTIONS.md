# Conventions of the R10 program cleanup

The program already ran in production. The cleanup therefore changes what a
person reads, never what the robot does (the rules below). The code changes
that came after it — the fixes of the Gestamp review and of the open items —
follow the rules of the last section, *Code changes after the cleanup*. `tools/check_cleanup.py` proves it
and must pass before every commit: after removing comments, blank lines and
indentation, every program must be identical to the archive as received,
except for the removals listed — with a reason — in
`tools/cleanup_allowlist.json` and `tools/cleanup_allowlist.d/*.json`.

## What may change

* Comments and fold titles: translated to English, corrected so they agree
  with the code, and completed with the signal they act on.
* `&COMMENT` lines (the navigator's comment column).
* Commented-out code and empty junk lines: deleted. When the commented-out
  line documents a check or feature that is switched off, it is replaced by
  a `;NOTE:` that says so in words.
* Unused declarations: deleted only through the allowlist, and only when the
  checker can prove nothing references them.
* Fold markers: moved or added so every `;FOLD` has its `;ENDFOLD`, with the
  right label. Code inside never moves.
* Unreachable modules that cannot be a service program: deleted (listed in
  the allowlist with the evidence).

## What never changes

* Any executable statement — not its text, not its order, not its case.
* Inline-form fold headers that carry form data (`;FOLD ... ;%{PE}%R ...%P ...`),
  and the lines inside such a fold. The smartPAD rebuilds the code from
  those parameters when someone opens the form. The only edit allowed is
  refreshing a stale tool name in the display text before `;%{` (for
  example `Tool[1]:GE4-002` -> `Tool[1]:TOOL 1`), and only in
  production-cycle modules whose paths ran with today's tool. Exceptions go
  through the allowlist; there is one: the second `OUT 106` form of
  RejectGE4 (form data `5:TRUE` -> `5:FALSE`, fold closed before the flag
  resets, F20). GripperTech form folds whose call was already commented out
  (grippers 2-4 in the clamp routines, F45) were removed: comment lines only.
* `;Params IlfProvider=ac_zoneilf ...` lines of AutomationCore inline forms,
  even where they disagree with the call (F21), and the GripperTech `;Params`
  lines of live gripper forms, even where they name another gripper (F31) —
  that needs a decision.
* Autogenerated blocks (`;START AUTOGENERATED -- DO NOT CHANGE`) and the
  folds owned by tech packages (`FOLD USER PLC`, `NutWeld PLC`,
  `Automation Core PLC`, `GRIPPERTECH LOOP`, `BASISTECH ...`, `AUTOEXT ...`,
  `INI`). Inside those folds only broken fold markers were repaired, stray
  blank lines removed and the German template comment `;Automatik extern`
  (sps.sub) translated. The user folds `USER INI` / `USER EXT` keep their
  titles; unused data in `USER EXT` was removed through the allowlist like
  any other declaration.
* Vendor files: KUKA system and tech packages, AutomationCore routines,
  NutWeld routines, GripperTech, BrakeTest, GlueTech (also the GlueTech
  template `Program/MoveToPurge.src`). Integrator edits found
  inside them are reported in [FINDINGS.md](FINDINGS.md), not touched. The
  vendor routines (`TP/**/*.src`, `bas.src`) are unchanged. In the
  declaration files `automationcoredata.dat`, `automationcoreroutines.dat`
  and `nutweldroutines.dat` only comments changed, except the unused
  integrator leftovers of the `Nut Tree` fold in
  `automationcoreroutines.dat`, removed through the allowlist.
* Line endings. CRLF files stay CRLF, LF files stay LF; the archive holds
  both and the KRC4 reads both.
* Numbers in comments that document calibration, e.g. the pressure table.
  On R10 the table and two of the three values in the code are not
  byte-swapped while the bus mapping swaps the word (F44): the numbers stay,
  a `;CHECK:` says so.

## How a comment is written

* English, ASCII, UPPER CASE for action comments (the style the programs
  already use), one line of at most about 100 characters.
* An I/O action names every signal it touches, with address and the label
  from [IO_MAP.md](IO_MAP.md):

  ```
  ;GUN OPEN - SIGNALS $OUT[472] dopw1_GunWork OFF, $OUT[471] dopw1_GunHome ON
  ;WAIT PART CLAMP CLOSED - SIGNAL $IN[467] (PART CLAMP CLOSED SWITCH) ON
  ;WELD START - SIGNAL $OUT[483] dopw1_WeldInit ON
  ;GRIPPER 1 OPEN - SIGNALS $OUT[249] do249Group1Home ON, $OUT[250] do250Group1Work OFF
  ```

  Outputs and inputs are written ON/OFF. A bit with only `Spare`/`Reserved`
  declared gets its description in parentheses.
* A comment says what the code does. Where the old comment contradicted the
  code, the new comment describes the code, and a second line asks the
  question for the commissioning engineer:

  ```
  ;LOWER PIN ADVANCE - SIGNALS $OUT[496] dopw1_ReturnPin OFF, $OUT[495] dopw1_AdvancePin ON
  ;CHECK: OLD COMMENT SAID LOWER PIN RETURN; THE CODE ADVANCES THE PIN HERE (F27)
  ```

* Three prefixes, used sparingly:
  * `;NOTE:` an explanation a maintenance technician needs;
  * `;CHECK:` something to confirm on the cell, with the finding number;
  * `;WARNING:` a trap — typically "do not open this inline form".
* Finding numbers (`Fnn`, `Cnn`) refer to [FINDINGS.md](FINDINGS.md).

## Module header

Every integrator module gets the Gestamp header (HOME.src already had one,
with "Line - Volvo"), after the
`INI` fold (or straight after the `DEF` line when there is no `INI` fold):

```
;********************************
; Gestamp Standards
; Line - BMW G65 (cell 03)
; Robot 03-10-R1 (BMW-03-10-R1-PNW1)
; Application - WELD NUT 1 (PN1) AT THE CENTERLINE PEDESTAL
;********************************
```

The device code is `PNW1` for the CenterLine pedestal nut welder and `MH1`
for material handling with EOAT 1 (pick, nut check, camera, drop, reject).
Robot-level modules (cell, the style and option programs, home, the repair
and pounce paths, mastering, collision reaction, electrode change, sps)
carry `BMW-03-10-R1` without a device code. Gestamp's program review of
2026-10-02 names the station BMW-03-10R1 (as on R20, where the cleanup had
first used `V431` from the WorkVisual project name). The exact format is to
be confirmed by Gestamp (C02). KRL module names cannot carry
the designation (no `-`, 24 characters), so it lives in the header and in
`&COMMENT`.

`.dat` files get no header; KUKA template comments such as
`;Make your modifications here` stay as they are.

## Code changes after the cleanup

From the Gestamp review on, the program changes on purpose. The cleanup
commit (`base` in `tools/code_changes.json`) stays proved by
`tools/check_cleanup.py --head <base>`; every later change is declared:

* `tools/code_changes.json` lists each change with the items it answers
  (Gnn, Fnn, Cnn) and the files it touches, and each deleted module with its
  reason. `tools/check_equivalence.py` fails on any changed, added or
  deleted KRL file that is not listed.
* Renames are free of review: `check_equivalence.py` compares signals by
  address, and `tools/renames.json` maps renamed identifiers and the named
  constants that replaced numbers. What it still shows is real logic and is
  reviewed by eye.
* I/O in executable code uses declared names, never `$IN[n]` / `$OUT[n]`.
  A bit that only has a `Spare` / `Reserved` name gets an AutomationCore
  style name (`do498UpperPinExtend`: prefix, address, function) in its fold
  of `automationcoreroutines.dat` — the address never changes. The KUKA
  standard inline forms (WAIT FOR, OUT) keep generating `$IN[n]` / `$OUT[n]`
  with the name in the form: they are not rewritten by hand.
* No GOTO and no labels: IF/ELSE, LOOP/EXIT, WHILE, REPEAT.
* Limits, pressures, times and program numbers are named constants in
  `$config.dat` (fold `CENTERLINE CONTROL` for the pedestal), not numbers in
  the code. Where the value is in doubt (the pressure words, F44) the
  constant keeps the value in use and its comment says so.
* Nothing is typed by hand inside an inline-form fold. A TRIGGER for a
  motion stands right before the motion's fold (the place KUKA's SYN OUT
  form uses); a reset that belongs after an AutomationCore form goes after
  its `;ENDFOLD`.
* A check of a part or a gripper comes before the command it protects (e.g.
  gripper empty before the first gripper command of a pick).
* Comments follow the rules above. A `;CHECK:` / `;NOTE:` / `;WARNING:` that
  described the old code is removed or rewritten in the same change.
* An office change is not finished until it is tested on the cell: its items
  get the state "Corregido en oficina - probar en celda" and a cell test in
  their closure criteria.
